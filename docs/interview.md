# 面试讲解手册 — 黄瓜病害智能诊断平台（设计思路 / 技术选型 / 追问应答）

> 所有答案均以仓库代码事实为准，关键处注明出处（文件:行）。指标数字口径见 `docs/评测报告_20260920.md` 与 `PROJECT_STATUS.md`。

## 一、设计思路

### 1. 为什么视觉检测与报告生成是两条分离的链路？

- **确定性分离**：检测（改进 YOLO11n，E2_gfix 冻结权重）输出的是**事实证据**——病斑框、类别、置信度、推理耗时（`cucumber-ai/app/routers/detect.py`）；报告生成是**语言组织**——LLM 只允许润色 4 个 editable 字段，病害类别/置信度/来源编号等 7 个 protected 字段由程序回填并逐项校验（`cucumber-ai/app/services/prompts.py:24-28`、`validators.py:38-44`）。
- **独立降级**：LLM 不可用时报告自动回退为确定性骨架（`report_status=fallback_to_skeleton`，`report.py:148-154`），检测链路完全不受影响——"交付率 100%"的机制基础。
- **独立验证**：检测侧用 test301 指标口径（mAP50=90.55）；报告侧用 12 项事实一致性校验（幻觉率 0.22% 的口径基础）。混在一起则两侧都无法单独度量。
- 业务侧（cucumber-admin）与智能体侧（cucumber-agent）也是同理的分离：admin 承接事务性操作（RBAC/审计/记录/复核流转），agent 只承接概率性推理。

### 2. 为什么 Agent 只做"不确定任务"？

平台里**能确定性完成的任务一律不用 Agent**：上传、检测、报告生成、记录查询、复核流转都是确定性代码——可靠、可测（admin 单测 36 项全绿）、可审计（AOP 操作日志落库）。Agent 只承接三类不确定任务：

1. **意图多样的自然语言交互**（"叶子发黄怎么办"可能是诊断/防治/用药任一意
   图）——三路融合意图识别（`intent_recognizer.py`）；
2. **需要知识检索与组织的问答**——RAG 工具 + 来源标注（`tools.py:156` 起）；
3. **需要判断的升级决策**（紧急灾情、用户质疑）——EscalationAgent 标准化交接（`agent_orchestrator.py:512-601`）。

收益：Agent 链路每次多次 LLM 调用，成本与延迟只花在真正需要推理的地方；Agent 宕机时主链路无损（admin 侧有降级处理与单测覆盖）。

## 二、技术选型

### 1. 为什么 EchoMind 编排层独立成服务（cucumber-agent）？

- **关注点分离**：admin 是 Java 事务性业务（Spring Security/RBAC/审计/RabbitMQ），agent 是 Python 概率性推理；混在一个服务里会互相拖累发布节奏与资源模型。
- **独立降级与伸缩**：agent 服务（8002）宕机时 admin 代理层友好降级，前端给出可读提示（有对应单测）；两边可独立扩缩容。
- **Runtime 复用**：EchoMind 是自主设计的通用多 Agent 运行时（意图/路由/工具治理/记忆/监控/评测），cucumber-agent 只是它的农业领域适配——同一 Runtime 可复用到其他垂直场景。

### 2. 为什么选 ChromaDB？

- **双模部署**：开发/评测用嵌入式 `PersistentClient` 零外部依赖即可跑；生产可切独立服务 `HttpClient`（`knowledge_base.py:44-63` 自动探测回退）。
- **内置 Embedding**：`add()`/`query()` 自动向量化，不额外依赖 Embedding API。
- **一库多 collection**：知识库（RAG）与情景记忆/用户画像用不同 collection 隔离，互不干扰。
- **已知局限（实测佐证）**：内置 all-MiniLM-L6-v2 是英文向量模型，对中文农业术语召回一般——2026-09-20 评测的裸检索 Recall@5 如实记录了这一点（见评测报告），改进方向是换中文向量模型或启用 pgvector（`retriever.py` 已在后续规划）。

### 3. 为什么意图识别用三路融合而不是单一方案？

| 方案 | 单用的问题 | 在融合中的角色 |
| --- | --- | --- |
| LLM 语义理解 | 延迟/成本高，偶发格式错误 | 主力（权重 70%），理解复杂语义与上下文 |
| Embedding 相似度 | 依赖向量质量 | 快速匹配常见表达（20%） |
| 关键词模式 | 泛化差 | 零延迟兜底（10%），LLM 失败时接管 |

融合逻辑在 `_vote`（`intent_recognizer.py:312-345`）：加权投票；LLM 失败自动降级到 embedding/pattern；融合置信度低于阈值（0.5）降级 OTHER，编排层随即给出澄清式回复（`agent_orchestrator.py:801-819`）。另有"细粒度修正"规则：泛意图（防治/问候）置信度不高且关键词命中细粒度意图（诊断/用药/转人工）时，以关键词路为准（`agent_orchestrator`/`intent_recognizer.py:340-342`）。

## 三、常见追问 10 问

### Q1. YOLO 的检测结果如何影响 LLM？

检测框经 `build_evidence`（`report.py:30-68`）按 **rule A**（最高置信框决定图像级类别）生成证据对象，同时打两个 flag：最高置信度 < 0.75 → `low_confidence_flag`；多类别框 → `class_conflict_flag`。证据进入确定性骨架后，`image_id / suspected_disease_class / prediction_confidence / evidence_ids / source_ids / 两个 flag` 共 7 个字段是 **protected**——LLM 的润色输出会逐字段与骨架比对，任何一个被动过都判 `protected_field_changed` 并触发纠错重润（仅 1 次），再失败就骨架回退。**LLM 永远无法修改检测结论**，它只能组织语言。

### Q2. "多模态融合"具体发生在哪？

不是让 LLM 直接看图。融合点是**结构化 schema**：视觉侧输出（类别 + 检测框 + 置信度）构成证据对象；文本侧用户补充的症状关键词随 `DiagnoseRequest.symptoms` 进入同一条流水线；知识库证据（source_id）注入生成上下文。最终五段式报告的每一部分都由证据与知识库组装而非自由生成。对话侧则是 Agent 通过 `diagnose_image` 工具调用同一条检测+报告链路（`api/main.py:166-182`），对话层拿到的仍是结构化报告。一句话：**视觉模型负责感知，LLM 负责知识推理，两者通过结构化 schema 汇合**。

### Q3. 幻觉率 0.22% 是怎么测的？

这是**论文第六章的既有口径**，定义权在 12 项事实一致性校验器（`validators.py` 逐行移植自论文 `validate_kimi_polish.py`，文件头注释明确"任何改动都会改变口径"）：必填字段完整、protected 逐项相等、source_ids 必须存在于知识库合法集合、低置信必须保留不确定性说明、冲突样本必须含冲突提示、可编辑文本每句须有骨架 3-gram 支撑（防自由创作）、不得把整叶框扩写为病斑级视觉观察（`VISUAL_CLAIM` 正则）、不得泄漏原始文件名/路径、不得 Markdown 包裹等。幻觉率 = 违反这些校验的输出占比（论文实验口径 0.22%）。平台侧完整保留了同一校验器 + 纠错重润 + 骨架回退机制。

### Q4. RAG 召回失败/召回不到怎么办？

四层兜底：

1. **查询改写 + 并行召回 + LLM 重排**（`tool_manager.py:312` `search_with_rewrite`）：一个查询改写成 3 个角度子查询并行检索，合并去重后 LLM 重排取 Top-K；
2. **工具熔断与降级**：连续失败触发熔断，fallback 明确告知"知识库暂时不可用"而不是编造（`api/main.py:132-141`）；
3. **Agent 侧诚实边界**：PreventionAgent 的 prompt 要求"检索不到的内容明确告知用户，不要凭印象编造"（`agent_orchestrator.py:468-472`），引用必须标注 source_id；
4. **升级路径**：知识边界无法满足时转人工专家复核。

2026-09-20 评测还实测了裸检索（无改写/重排）的 Recall@5 作为知识库能力下限，具体数字见评测报告。

### Q5. 为什么不用纯 CNN 分类，而要用目标检测？

- 分类只给图像级标签，**没有病斑定位**；检测框本身就是可解释证据（前端叠加展示、专家复核依据）；
- **多病斑/多类别并发**场景分类直接失效，而检测的 `class_conflict_flag` 正是依赖多框才能定义；
- **开放集问题**：训练集外的病害/非叶片图片，分类器会硬判一个已知类；检测链路靠低置信门控（<0.75 自动转专家复核）+ 用户纠错反馈闭环兜底；
- 与论文改进 YOLO11n（E2_gfix，test301：P=92.48 / R=87.37 / mAP50=90.55）对齐，指标口径可复现。

### Q6. 意图识别为什么不用微调小模型？

没有标注语料，且意图体系会随业务演进（6 类意图的定义写在 prompt 里，改定义零训练成本）。三路融合在 108 条用例上的实测准确率见评测报告；同时支持**在线学习**——纠正样本通过 `learn()` 加入模板并清缓存（`intent_recognizer.py:194-201`），等于低成本的持续迭代通道。真到数据量足够时，LLM 路可以平替成微调分类器，接口不变。

### Q7. LLM-as-Judge 可信吗？偏差怎么控制？

- 固定 Judge prompt + `temperature=0.0`，同输入评分可复现（`evaluator.py:134-137`）；
- 拆成六个维度（相关性/准确性/完整性/有用性/诊断准确性/用药安全性），降低单一总分的主观性；
- Judge 调用失败不静默计 0 分，而是置 `judge_failed` 标记并按 0.5 中性分计入，报告里能看到失败样本数；
- 与历史基线做回归对比，指标退化 >5% 自动告警（`evaluator.py:407-421`）；
- **局限明示**：Judge 与被测 Agent 用同一模型存在自评偏差，代码 docstring 明确建议"定期用人工标注校准"（`evaluator.py:96-98`）。

### Q8. 为什么用药建议要单独拆一个 Agent？

用药是**合规风险最高**的环节（禁限用农药、安全间隔期直接关乎食品安全）。独立 MedicationAgent 带来：独立 system prompt 与 `temperature=0.0`（最保守采样）、专属合规工具（`check_medication_safety`）、Judge 单独维度 `medication_safety` 专项度量、明确的移交条件（用户坚持禁限用→转人工）。出问题时的影响面被限制在这一条链路内。

### Q9. 对话记忆是怎么做的？

三层（`memory/conversation_memory.py`）：

1. **工作记忆**（Redis）：最近若干轮原文，供意图识别与 Agent 上下文；
2. **情景记忆/用户画像**（ChromaDB）：向量化历史，按当前问题检索相关片段，画像异步更新不阻塞响应；
3. **摘要压缩**：超过窗口的历史用 LLM 压成 2-3 句摘要（保留最近 5 条原文），摘要合并限长，生成失败有占位回退。

### Q10. 低置信或不确定样本怎么处理？

四条路径全部落在代码里：

1. 检测最高置信度 < 0.75（含无检出）→ `low_confidence_flag` → 骨架强制生成不确定性说明（校验第 6 项卡住不放行）→ admin 自动创建 **UNCERTAIN 复核单**，专家复核页有专用标签；
2. 多类别检测框 → `class_conflict_flag` → `uncertainty_note` 必须含"冲突"（校验第 7 项）；
3. 用户在记录详情页主动提交"诊断有误"纠错反馈 → 专家复核流转；
4. 对话侧用户质疑/紧急灾情 → EscalationAgent 创建复核反馈（关联 record_id 时确定性调用，不经 LLM）。

形成"诊断 → 反馈 → 复核 → 迭代"闭环，复核数据反过来就是后续评测集与知识库的扩充来源。
